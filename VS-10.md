# VS-10 — Settlement images and region labels from game data

Status: plan. Predecessor investigation: the Python POC (`C:\Users\tony\AppData\Local\Temp\opencode`)
extracted the assets but placed them with hand-fitted constants; this plan replaces
every fitted constant with values decoded from the game files.

---

## 1. What VS-10 delivers

The composite/data views render the world-map fields. VS-10 adds the game's own
map overlays on top of them, positioned the way the game positions them:

1. **Settlement images** — the detailed top-view town art
   (`cd_knowledgeimage_worldmapicon_*_topview`) drawn at their faction-node
   positions with the game's own sizes and anchor offsets.
2. **Labels** — the game's whole label system, not just the big titles:
   texture-backed region titles (kingdoms at scale 2.2, territories and
   areas at 1.4/0.9/0.6/0.5) plus font-rendered labels for towns, areas and
   seas — every string from the game's localization table, never a codename.
3. **The world→map projection**, taken from game data, shared by the exporter
   and the renderer so overlays and fields can never drift apart.

Non-goals: POI/pin markers (`uimaptextureinfo.staticinfo` — runtime markers,
not placement), the abyss hex grid interaction, fog-of-war, zoom-dependent
icon swapping (Greymane lv1–5 are exported; level selection is a later step).

## 2. The evidence (all decoded from game files)

### 2.1 The map plane and the projection

- The game's world-map UI plane is **8192 × 8192 CSS px**
  (`worldmapview.css:120-121`: `.worldmap-fog` / `.worldmap-sea`).
- `fieldinfo.staticinfo` (pack `0008`, `gamedata/fieldinfo.staticinfobody`),
  record `MainField_UIMap_Texture` (key 10), carries — after the four field
  floats — three floats `(x_min, z_top, span) = (-16384, 8192, 19456)`.
  The worldmap SDF textures (32768² px; the 8192 previews are ÷4) cover
  **x ∈ [-16384, +3072], z ∈ [-11264, +8192]** — a 19456² world window.

  The projection onto the 8192 UI plane is therefore, exactly:

  ```text
  px = (x - x_min) · 8192/19456 = 0.4210526·(x + 16384) = 0.4210526·x + 6898.5
  py = (z_top - z) · 8192/19456 = 0.4210526·(8192 - z)  = 3449.3 - 0.4210526·z
  ```

  (z is north-up; py flips.) `8192/19456 = 8/19 = 0.4210526…`
- Cross-checks, all exact:
  - `MainField` (key 1) floats `(-15359, -9215, 1023, 5119)` and its tile
    ints `(-240, -144, 15, 79)` — 256×224 tiles of **64 world units**
    reproduce the rect exactly.
  - `MainField_UIMap` (key 99999) floats `(-13350, -7120, -1050, 4070)` and
    tiles `(-209, -112, -17, 63)` — ditto.
- Empirical validation (game data only): projecting all 1105 positioned
  `factionnode` entries onto the game's own land/road SDF previews peaks at
  exactly S = 0.421053 with **zero** offset correction (land 0.952 vs 0.918
  for the POC's fitted constants; road-distance median 5.8 px vs 14.3 px).

### 2.2 Settlement images

- Position: `factionnode.staticinfo` world position (`Node_*` records; x ∈
  [-13122, 0], z ∈ [-7012, 3557]).
- Size and anchor: `worldmapicon.css` (game UI), classes
  `.WorldmapIcon_Setting_Faction_*`, one per settlement, e.g.

  ```css
  .WorldmapIcon_Setting_Faction_Demeniss { width: 230px; height: 230px;
      translate-x: -50.900002%; translate-y: -49.549999%;
      background-image: textureid(cd_knowledgeimage_WorldmapIcon_Town_Demeniss_00_topview); }
  ```

  CSS px = map px on the 8192 plane; the translate percentages are of the
  element's own size, applied after `top:50%; left:50%` anchoring. The POC's
  "hand-tuned" values were verbatim these rules — the mechanism is the game's,
  only the projection was wrong (5 % small, ~290 px drift at the cloud edges).
- Component wiring: `worldmapicon.thtml:168-232`
  (`WorldmapIcon_Setting_Faction_Demeniss|Hernand|Pailune|Pailune1|Delesyia|
  Varnia|Castle_Calphade|Town_Calphade|Urdavah|Tommaso|Camp_Her_GreymaneCamp_lv1..5`).
  Note `Pailune1` is the lower half-image (181.7 × 90.85, translate-y +59.80).
- Assets: standalone DDS per settlement under `UI/texture/…`.

### 2.3 Region labels

- Texture id → file + rect: `cd_worldmap_regiontitleimage_eng.xml`
  (`GetRect="0,0,512,512"` etc.). Faction-region titles are ids 2–6; sub-region
  titles 12–22, 100xx/101xx, 110x/120x/130x, 510xx.
- **Every region has a display name — the label text pipeline.** The decimal
  string in each `regioninfo` record is `(key<<32)|0x110`, and that is the
  localization id: `region.paloc` (localized pack, encrypted — decrypt with
  the entry name, then LZ4) maps it to the display text. 1007 records,
  1007/1007 region keys covered. Format: `[u32 0x11][u32 0][u32 klen]
  [decimal loc id][u32 tlen][utf8 text]`. Proof the loc table is mandatory —
  internal codenames never render:
  key 2 (Region_Kweiden) → **"Pailune"**, 4 (Region_Akapen) → **"Hernand"**,
  5 (Brondell) → "Delesyia", 6 (Delpheon) → "Demeniss", 3 → "Crimson Desert",
  12 → "Tribal State of Pailune", 14 → "Kingdom of Demeniss",
  1102 → "City of Pailune", 10181 (Region_Ocean) →
  "The Great Ocean of Pywel" (the sea label).
- **Label kinds on the map** (all text from the loc table): kingdom titles
  (texture, scale 2.2), territory/area titles (textures, scale 1.4/0.9/0.6),
  sea labels (same title components with the `material-worldmap-region-name-sea`
  material — `_sea` thtml variants), and town/point labels rendered as font
  text next to icons (`BaseIconText`, `font-text-*` classes).
- **Title id = regioninfo key.** 97 of the 148 atlas ids exist verbatim as
  `regioninfo.staticinfo` keys with matching semantics: 2 = Region_Kweiden,
  3 = Region_Crimson_Desert, 12 = Region_Pailunese_Territory, 1102 =
  Region_Pailune_Town, 1201 = Region_Hernand_Town… The kingdom records carry a
  cross-link u32 (`key<<16`) pointing at their territory region (Kweiden→12,
  Akapen→13 = Region_Hernandian_Territory, Delpheon→14, Brondell→15,
  Crimson_Desert→17) — the same numbering, confirming the rule. The 51
  unmatched atlas ids (16, 19–22, 101–104, 201, 301–305, 51003–51006, …) have
  no region with that key in this table; M3 renders each once and logs it
  rather than assuming anything.
- **`regioninfo.staticinfo` is the region hierarchy, not shapes.** Record
  layout (fully decoded): `u16 key, u32 strlen, name, const u32 0x01101100`
  (low byte doubles as the name terminator), `u32 key<<16`,
  `u32 strlen2<<16`, decimal string `(key<<32)|0x110`, zero pad, then either
  a **child list** (`u32 count` + `count × u16` region keys — verified 100%:
  all 846 child values across 16 regions resolve to existing keys) or, for
  kingdom records, the territory cross-link; tail ends in a u32 crc. Pywel
  (key 1) lists 199 children — the six kingdoms plus every named area.
  Areas are children of territories, territories of kingdoms, kingdoms of
  Pywel — and **every map node has its own region** (`Region_Node_Her_…`,
  keys 41xxx/42xxx), so node → region-chain membership is explicit game data.
  The single geometry payload is Region_Abyss (48 values in a 16384-grid —
  the hex area).
- Scale and rotation: `worldmapicon.css:1126-1160`, classes
  `.worldmap-region-title-<id>` — `scale-x/y` 2.2 (faction regions), 1.4, 0.9,
  0.6, 0.5; `rotate-z` in degrees (Crimson Desert = −21, others −52, −50, −7,
  −5, −3). Generic `WorldmapIcon_RegionTitle_<WxH>_<scale>` thtml components
  set `use-background-image-size="true"` → draw size = atlas rect × scale.
- Title textures are **SDF-encoded** (the POC's `sdf_to_rgba` bands
  0.42–0.55 / 0.75–0.90 over a /133 normalisation recover clean coverage) —
  they can be rendered as true signed distance at runtime, crisply at any zoom.

## 3. Architecture decisions

1. **Overlays are two export manifests, not a scene change.** The scene
   contract ([[concept.sdf-scene-contract]]) stays untouched: no new reserved
   names, no scene-file edits. The renderer draws overlays the same way it
   draws the contour overlay — a separate pass over the finished scene frame
   (precedent: `sdf-component/src/overlay.rs`).
2. **The projection lives in the manifests.** `settlement.json` and
   `labels.json` each carry `x_min / z_top / span / plane` verbatim from
   `fieldinfo`; the renderer never hardcodes map constants. The SDF field
   export gains the same constants in its manifest (§5.3) so field-uv ↔
   map-px is derivable on both sides from data.
3. **Positions are resolved at export into the two JSONs.** `settlement.json`
   carries per-settlement world positions (verbatim factionnode values) and
   CSS size/anchor numbers; `labels.json` carries per-label world anchors
   (region-subtree node centroids) with display text from the loc table.
   Nothing is hand-authored and nothing is pre-baked in pixels — the
   renderer applies the projection at draw time, so the manifests stay
   resolution-independent and the component's field-uv view machinery
   applies unchanged.
4. **Icons are packed offline into one RGBA8 atlas** (`atlas_icons.rgba`);
   `settlement.json` stores uv rects. Runtime uploads one texture, one bind
   group — no per-icon textures.
5. **Titles keep their SDF channel** in a second atlas (`atlas_titles.r8`)
   and render as distance fields with the game's scale/rotation applied in
   the overlay shader; font labels render from the glyph atlas. Crisp at
   every zoom — this is the repo's own medium.

## 4. Data — `settlement.json` and `labels.json`

Two manifests, built by one export run straight from the game data (nothing
hand-authored), both self-contained: each carries the projection it was
built with — a golden test asserts the two copies are byte-identical, since
both are written from the same decoded `fieldinfo` values. Written to
`<data_dir>/overlays/`, textures beside them.

`settlement.json` — the settlement images:

```jsonc
{
  "version": 1,
  "projection": { "x_min": -16384.0, "z_top": 8192.0, "span": 19456.0, "plane": 8192.0 },
  "atlas": { "file": "atlas_icons.rgba", "size": [4096, 4096], "sha256": "…" },
  "settlements": [
    { "name": "Demeniss", "node": "Node_Dem_DemenissCastle",
      "world": [-8062.0, 473.5, -3539.0],   // verbatim factionnode pos
      "rect": [0, 0, 230, 230],             // atlas uv rect, px
      "size": [230.0, 230.0],               // CSS px on the 8192 plane
      "anchor": [-50.900002, -49.549999],   // CSS translate % of element size
      "stage": null }                       // "lv1".."lv5" for camp variants
  ]
}
```

`labels.json` — every label, texture-backed or font:

```jsonc
{
  "version": 1,
  "projection": { … identical object … },
  "atlas": { "file": "atlas_titles.r8", "size": [2048, 2048], "sha256": "…" },
  "titles": [                           // texture-backed (title id = region key)
    { "id": 3, "key": 3, "text": "Crimson Desert",
      "rect": [0, 0, 512, 512],
      "scale": 2.2, "rotate_z": -21.0,
      "world": [-6656.0, -1525.0] }     // centroid of the region's node set
  ],
  "labels": [                           // font-rendered: towns, areas, seas
    { "key": 1102, "text": "City of Pailune", "kind": "town",
      "world": [-9640.7, 213.7], "size": [220.0, 40.0], "style": "normal" }
  ]                                     // style: normal | sea
}
```

Rules:

- Positions are **pre-resolved at export** — no node tables ship in the
  manifests. A settlement's `world` is the verbatim factionnode position; a
  label's `world` is the centroid of its anchor region's node subtree
  (region hierarchy + `Region_Node_*` membership, §2.3).
- Every `settlements[].node` must exist in `factionnode` (export rejects,
  naming the node); every title/label `key` must resolve in `regioninfo`
  and the loc table (export rejects, naming the key). A region whose
  subtree contains no positioned node is a diagnostic and gets no label.
- `titles` are exactly the atlas ids whose regioninfo key exists; the 51
  unmatched atlas ids go to the M3 log, never into the manifest.
- `rect` must fit its atlas; `sha256` over both atlases is verified at
  load, mirroring the field manifest's trust model — the GUI parses no
  DDS, ever.
- Variants (`GreymaneCamp_lv1..lv5`, `Pailune`/`Pailune1` halves) ship as
  separate entries; the renderer draws the un-staged set, and `stage`
  marks what the zoom-stage follow-up will switch between.

## 5. Work breakdown

### 5.1 `sdf-offline` — extraction

- `config/extract.rs`: `DEFAULT_PACKS = ["0012", "0008"]`; add includes:
  `gamedata/fieldinfo.staticinfo*`, `gamedata/factionnode.staticinfo*`,
  `gamedata/regioninfo.staticinfo*`, `worldmapicon.*`, `worldmapview.*`,
  `cd_worldmap_regiontitleimage*.xml`, `cd_knowledgeimage_worldmapicon_*`,
  `cd_worldmap_regiontitle_*`. (Order matters not; both packs are scanned.)
- Localization: a new config key `[extract] localization_pack = "00XX"` —
  the EN pack containing `region.paloc` (POC located it among 0019–0033;
  resolved once through the GUI picker like `game_root`). The entry is
  encrypted: decrypt with the entry file name (`paz/crypto.rs`, same path
  the POC used) before LZ4.
- The existing `run/extract.rs` loop needs no changes — it already scans a
  pack list and globs entry paths.

### 5.2 `sdf-offline` — parsing (new module `src/gamedata/`)

- `staticinfo.rs`: shared table reader — u16-or-u32 key (per-file),
  count/offset header (`stride` detected: 8 → `<II>`, 6 → `<HI>`), records =
  key, u32 strlen, name. Record payloads parsed per table.
- `fieldinfo.rs`: record layout is `u32 key, u32 strlen, name, const u32
  0x04F6D06D` (the const's low byte doubles as the name terminator), then an
  f32 block, then an i32 block. Floats = 4 world bounds + extras; assert
  `MainField_UIMap_Texture` yields the window triple `(-16384, 8192, 19456)`;
  derive and emit `projection`.
- `factionnode.rs`: key u32, name, blocked, knowledge/skilltree/research,
  store/royalsupply u16, memo string, two u32 arrays, pos xyz f32, radius
  f32 (layout per POC `parse_fn2.py`).
- `regioninfo.rs`: hierarchy parser per §2.3 — child lists (reject the
  export if any child key fails to resolve, naming the parent), the kingdom
  territory cross-link, and `Region_Node_*` names bound to factionnode
  entries (a node-region naming a node that factionnode lacks is a
  diagnostic, not an error). Emits per-region node sets; the label anchor is
  the centroid of the anchor region's node set, stored in world space and
  projected at draw time (§2.1).
  Region_Abyss's geometry payload is parsed but unused in M1–M3.
- `loc.rs`: `region.paloc` parser (tag-`0x11` records, §2.3) → region key →
  display text. The overlay export rejects if any region key used by a title
  or label has no loc entry (naming the key); the resolved text is written
  into each label/title entry (`text`), never kept as a separate dump.
- Labels: every region whose subtree contains map nodes gets a label entry —
  `kind` = `town` for `Region_*_Town`/node-regions of settlement nodes,
  `sea` for regions the thtml binds to the `_sea` material, `area`
  otherwise. Regions with a texture title are drawn from the texture; the
  rest render as font text (M3).
- Title anchors: a title anchors on its own region's node set — kingdom
  titles (2–6) on the kingdom subtree, territory titles (12–15, 17) on
  theirs; the kingdom records' territory cross-link (§2.3) is parsed and
  emitted for the docs, not needed for anchoring.
- `css.rs`: minimal tokenizer for the two game CSS files. Extract, per
  `WorldmapIcon_Setting_Faction_*` class: width/height (px), translate-x/y
  (%), `textureid(...)`; per `worldmap-region-title-<id>`: textureid, scale,
  rotate-z. Whitespace/comment tolerance only — no general CSS engine.
- Node ↔ icon binding: normalize the node name (`Node_Cal_CalphadeCastle` →
  `Castle_Calphade`, `Node_Crim_Urdavah` → `Urdavah`, …) and match a CSS
  class; misses are emitted as diagnostics, not errors (a table override
  lives in `[extract.overlays]` config for any stragglers).
- `atlas.rs`: decode the referenced DDS to RGBA8, pack shelf-first into a
  4096² atlas (grow ×2 on overflow), write `atlas_icons.rgba` + rects;
  titles are stored separately as R8 (single channel = the SDF distance) in
  `atlas_titles.r8` with their own rects. DDS decode: the tile families are
  uncompressed 8-bit today; the icon/title DDS are not — add BC1/3/5/7
  decode via `texture2ddecoder` (pure Rust, RGBA8 out, no other deps)
  behind `dds/decode.rs`. If a format shows up that we cannot decode, fail
  the overlay export naming the file — never emit a wrong pixel.

### 5.3 `sdf-offline` — export

- New `run/overlays.rs` producing, in one run (schema §4):
  `overlays/settlement.json` + `overlays/atlas_icons.rgba`, and
  `overlays/labels.json` + `overlays/atlas_titles.r8` — same
  manifest-record/progress conventions as `run/extract.rs`. The projection
  object is written from one decoded value into both files; the writer
  asserts the two serializations are identical before finishing.
- `config::Overlays` section (offline config, `[extract.overlays]`):
  `dir` (default `overlays`), `atlas_size`, and the node↔class override
  table.
- Field manifest gains `world_window` (x_min, z_top, span) in
  `export/manifest.rs` — additive, version stays 1 with an optional field
  (absent = legacy export; overlays then refuse to load with a named error).

### 5.4 `sdf-component` — data

- `src/data/overlay_manifest.rs`: loads both files, verifies structure (the
  §4 rules), that the two projection blocks are equal (load error naming the
  mismatching file if not), and the sha256 of both atlases; immutable once
  loaded; failures named like the field manifest's.
- Reuse the `config:` scheme path rewriting from the scene loader; a scene
  does not reference overlays — the shell decides whether overlays render
  (config-driven, §5.6), so no scene-file changes at all.

### 5.5 `sdf-component` — renderer

- `src/renderer/overlays.rs` (new, sibling of `overlay.rs`): one pipeline,
  triangle-list instanced draws, alpha blending over the scene frame, run
  after the scene pass and after the contour pass.
- Uniforms per frame: the projection constants, the current view
  (`view_center`, `params.z`), plane size. Vertex stage expands
  [map-px rect] → [field-uv] using the identical formulas as §2.1, so the
  existing pan/zoom/viewport-clamp machinery applies for free: overlays pan
  and zoom with the map and clamp identically.
- Icons: sample the RGBA atlas (linear), premultiply, mix by `weight`.
- Titles: sample the R8 SDF channel, threshold with the game's band
  (0.42–0.55 / 0.75–0.90 over 133) — reused as smoothstep widths — rotate by
  `rotate_z`, scale by `scale`, ink = paper tone from the existing palette
  constants.
- Font labels: regions without a texture title draw the label entry's
  `text` as glyphs — glyph atlas built at load with `ab_glyph` (pure Rust,
  no system-font dependency; the game's own label font is not shipped in an
  extractable form, so VS-10 uses the shell's paper-map font as the stand-in
  and the docs note it). Same anchor rule, size from the entry's `size` in
  plane px, ink from the palette; the entry's `style` (`normal` | `sea`)
  selects the letterspaced sea treatment.
- Staging/readback/presentation are untouched: overlays render into the same
  offscreen target before the copy.
- LOD note: the contour overlay contours field 0 only (documented
  behavior); overlays are independent of the LOD slider.

### 5.6 `sdf-ui` — shell

- `config.toml` new section, shipped in `DEFAULT_TEMPLATE`:

  ```toml
  [overlays]
  enabled      = true
  titles       = true
  opacity      = 1.0        # 0..=1, both layers
  ```

- `Config::check()` rejects opacity outside 0..=1 (naming the key), same
  style as the composite checks.
- Control bar gains one toggle (overlays on/off) + the opacity slider reuses
  the existing slider component; status bar shows
  `overlays: N settlements, M labels` when loaded, or the load error
  verbatim.

### 5.7 Docs

- `docs/concept.sdf-overlay-placement.md` (new, soul doc): the §2 evidence,

- `docs/concept.sdf-scene-contract.md`: one sentence under Data scenes —

## 8. Risks and open questions

1. **The 51 unmatched title ids — handled, not assumed.** They have no region
   with the same key in the extracted table; M3 renders each once and logs
   the image next to its id, so what each one is gets settled by observation
   (most plausible: ids from another build/patch or reserved slots). They
   block nothing: every region that actually exists has a loc name and
   therefore a label, texture or font.
2. **`bitmapposition.staticinfo`** (varint per-row RLE spans over a ~16k
   grid, rows stepping 128) remains the game's baked overlay geometry.
   Optional stretch goal after M3: if decoded, titles/labels gain an
   optional `bitmap_anchor` world-space field for shape-exact anchoring —
   additive and schema-compatible. Not required for VS-10 acceptance —
   node-set centroids already come from game data.
3. **Icon semantics at zoom**: the game swaps icon sets by zoom stage
   (`changePoint`, `snap-distance`), and font labels fade by zoom too.
   VS-10 draws the full-resolution set always; the stage machinery is
   recorded in the docs as follow-up.
4. **Font fidelity**: the game's label font is not recoverable as a
   extractable font file; VS-10 renders labels with the shell font at
   game-derived sizes. Documented; swapping the TTF later is a config
   change, not a pipeline change.

No open items remain for M1–M4: every placement constant, binding, label
text, and anchor is decoded from game files and covered by golden tests.
Items 2–3 are additive upgrades; item 4 is a documented stand-in.
