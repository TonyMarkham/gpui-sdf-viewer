# VS-10 — Composite view: one navbar entry that stacks every configured layer

Status: planned · Depends on: VS-20 export manifest (shipped) · Touches: `sdf-offline`, `sdf-component`, `sdf-ui`, `docs/`

## Goal

Today the left navbar turns **one** view on at a time: each `scenes/*.wgsl`
file binds exactly one manifest layer (`coast`, `river`, `road`, …) and
selecting another scene replaces it. VS-10 adds a **composite view**: a
single navbar entry that renders several game fields stacked in one frame,
with the layer list owned by `config.toml` — not by scene files.

    [composite]
    layers = ["coast", "river", "road", "mountain", "abyss_hex"]

The array is the source of truth for both *which* layers compose and their
*paint order* (bottom → top). An empty array hides the composite entry; the
five shipped recipe routes are the defaults, i.e. "all available layers" out
of the box.

Non-goals: per-layer visibility toggles at runtime, drag-to-reorder, editing
the composite recipe in a user scene file — all natural VS-11+ follow-ups
that fall out of the surfaces built here (the config array, the generated
scene source, the recipe table).

## Current behavior (the gap)

- `Navigation` (`crates/sdf-ui/src/component/navigation/mod.rs`) lists
  `SceneLibrary` entries — one button per discovered `.wgsl` file — and
  `App::select(index)` loads exactly one scene into the canvas
  (`crates/sdf-ui/src/state/app.rs:143`).
- The scene contract is single-field: `// sdf-scene: data = …` + `layer = …`
  select **one** entry from the VS-20 manifest's `layers` array
  (`crates/sdf-component/src/scene/mod.rs:107`, `data_request.rs`).
- The renderer binds **one** field texture array at `@group(0) @binding(1)`
  (`crates/sdf-component/src/renderer/mod.rs:139`), one array layer per grid
  tile of that single field; the prelude's `field(p)` samples it
  (`crates/sdf-component/src/scene/mod.rs:255`).
- `Config` (`crates/sdf-offline/src/config/mod.rs:76`) carries `paths`,
  `extract`, `sdf` — no composite section.

## Design overview

Every VS-20 layer of an export shares the same geometry by construction —
`Export::new` stamps `size = TILE_GRID_EDGE * TILE_EDGE` (16·16 tiles of
512²) and the same mip table on every layer
(`crates/sdf-offline/src/export/mod.rs:55`) — so a composite can bind **one
field texture array per configured field** and let the generated prelude
sample them side by side: field *k* binds as `t_field_k` at its own binding
slot, and the generated helper `field_k(p)` samples exactly that texture.
Single-field scenes keep today's exact binding (`t_field` at binding 1, the
one-array-per-tile layout); the composite generalizes the bind group to N
textures.

Why not stack all fields into the existing single `t_field` binding: wgpu 29
`Limits::default()` (what `Renderer::new` requests,
`crates/sdf-component/src/renderer/mod.rs:125`) guarantees only
`max_texture_array_layers = 256` — exactly one 16² field. A stacked
two-field texture needs 512 layers and is rejected on default limits unless
device bring-up starts demanding adapter-specific limits, which would risk
`request_device` failing for every scene on constrained hardware. Per-field
bindings stay inside the guaranteed box (`max_sampled_textures_per_shader_stage
= 16` covers up to 15 composite fields).

What changes, per crate:

| Crate | Change |
| --- | --- |
| `sdf-offline` | New `[composite]` config group: `Composite { layers: Vec<String> }`, defaults, validation in `Config::check()` |
| `sdf-component` | `layers` header directive (multi-field `DataRequest`), multi-field `SceneData`, per-field textures and bindings in the renderer, generated `t_field_0..n` / `field_0..n` prelude helpers |
| `sdf-ui` | A synthetic **Composite** navbar entry, the composite scene source assembled from config + a recipe table, staged through the existing `config:` rewrite path |
| `docs/` | Scene-contract update (`layers` directive, composite view) + soul annotations |

The uniform block, the samplers, the overlay pass, pan/zoom, the LOD slider,
and the contour overlay all keep working unchanged — the composite is a data
scene like any other, and every existing control keeps working. The one
invariant that intentionally gives way is "one bind group shape serves both
scene classes": a composite scene's bind group carries N textures instead of
one.

## Config surface

Added to `DEFAULT_TEMPLATE` (`crates/sdf-offline/src/config/mod.rs:29`),
keeping the file's comment style:

```toml
[composite]                  # the composite view: layers stacked bottom-to-top
layers = [                   # paint order; each name must be an export route
    "coast",
    "river",
    "road",
    "mountain",
    "abyss_hex",
]
```

Semantics:

- Each entry must name an export route — a `[sdf.tiles]` key or an
  `[sdf.export.extra]` name (`Config::routes()` already enumerates both).
  `road_wagon` and `blur_height` are therefore legal; they render with the
  neutral fallback recipe until given real ones.
- Duplicates are a config error; an empty array is **valid** and means "no
  composite entry in the navbar" (the feature is off, not broken).
- `[composite]` is a view concern: the extraction pipeline ignores it.
  `Config::save_to` keeps its format-preserving `paths`-only edit, so
  hand-tuned composite arrays survive GUI saves untouched — same contract as
  `[extract]` today (pinned by the existing hand-tuned-save test).
- Where config errors surface is a deliberate split: `check()` runs on the
  extraction path (as today), not at app startup — the GUI loads a config
  with an invalid composite layer name without complaint, and the failure
  surfaces only when the entry is selected, as the manifest's
  unknown-layer error in the status bar. Startup-time reporting would add a
  config-error channel to `OfflineState` for no gain over the existing
  scene-load error path.
- Migration: existing user `config.toml` files simply lack the group; the
  `#[serde(default)]` field yields the defaults, and the shipped template is
  only written on first run. Users who want the group hand-copy it from the
  template (or delete their config to regenerate).

Structural change (`crates/sdf-offline/src/config/composite.rs`, new module
alongside `sdf.rs` / `export.rs`):

```rust
pub struct Composite {
    pub layers: Vec<String>,   // paint order, bottom → top
}

impl Default for Composite {
    // coast, river, road, mountain, abyss_hex — every recipe route
}
```

`Config` gains `#[serde(default)] pub composite: Composite`. `Config::check()`
extends with two rejections, both naming the offender:

- `composite layer "X" is not an export route` — X ∉ `routes()`
- `composite layer "X" is listed twice` — duplicates

## Work plan

### 1. `sdf-offline` — the `[composite]` group

- New `config/composite.rs`: `Composite` struct, `Default` = the five recipe
  routes in paint order, serde derive matching `Sdf`/`Export` style.
  Reuse the route-name consts (`COAST_ROUTE`, …) instead of repeating
  literals.
- `config/mod.rs`: add `composite` to the `Config` struct and to
  `DEFAULT_TEMPLATE`; extend `check()` per the semantics above.
- No `save_to` change (format-preserving edit already preserves the group).
- Tests (`config/tests.rs`):
  - the shipped template still equals `Config::defaults()` (existing test
    guards this — it must keep passing with the new table);
  - `check()` rejects an unknown layer name and a duplicate, accepts the
    defaults and an empty array;
  - a hand-written subset (`layers = ["coast", "road"]`) round-trips
    load → save → load with comments preserved.

### 2. `sdf-component` — scene contract: the `layers` directive

- Header grammar (one more alternative, documented in the module doc):

  ```text
  // sdf-scene: data = "…"
  // sdf-scene: layers = "coast,river,road"   // composite form
  // sdf-scene: layer  = "coast"              // single-field form
  ```

  Pairing rule: `data` + (`layer` **xor** `layers`), or neither. Carrying
  `layer` and `layers` together is a parse error; an empty item in the
  `layers` list is a parse error naming the value. Order in the list is
  paint order and is preserved everywhere.
- `DataRequest` gains `layers: Vec<String>` (replacing the single `layer`
  string; a 1-entry list is legal). `SdfScene::from_file` resolves every
  entry from the manifest and builds the multi-field `SceneData`.
- `SceneData` becomes `fields: Vec<SceneField>` where `SceneField` holds
  `layer`, `tiles` (and the geometry below); `SceneData` keeps the shared
  shape: one `grid`, one `levels` chain. `SceneData::load(manifest, &layers)`
  validates, per pair of fields, that **grid and mip-level count agree**
  (`field "b": grid 8 differs from field "a": 16` / same wording for
  levels) — the shared-geometry assumption is what lets every field reuse
  the one `field_coord(p)` decomposition. Validation is byte-exact: every
  field's mip table must equal the first field's (same count *and* same
  sizes), with the error naming the first divergent pair — equal counts
  alone would let hand-edited manifests disagree silently. Call sites to
  update: `renderer::create_field_texture`, `ensure_overlay`,
  `canvas/state.rs` (`has_data`, `field_level_count`), `scene::module_source`,
  `data_key`.
- `data_key()` becomes `manifest#layer1+layer2+…` — ordered, so the
  renderer's field cache, the skip-unchanged check, and the failure cache
  distinguish every composite from every single-field scene.

### 3. `sdf-component` — prelude and renderer

- `field_helpers(grid, levels)` → `field_helpers(grid, levels, n_fields)`.
  For `n_fields > 1` it now emits one texture binding and one helper per
  field, next to the existing constants:

  ```wgsl
  @group(0) @binding(4) var t_field_1: texture_2d_array<f32>;   // generated per field k
  fn field_1(p: vec2f) -> f32 {
      return textureSampleLevel(t_field_1, s_field, field_coord(p).uv,
                                field_coord(p).layer, u.params.x).r;
  }
  ```

  Binding slots: field 0 keeps binding 1 (today's `t_field`); fields
  1..n-1 take bindings 4, 5, … (0..3 stay uniform + field 0 + two
  samplers). `field(p)`, `field_lod`, `field_raw` stay bound to field 0,
  so single-field scenes compile to byte-identical modules as today and
  the contour overlay (which samples `field_lod`) keeps contouring the
  **first** composite layer — documented behavior. Reserve `t_field_`,
  `field_` in the reserved-names list.
- `Renderer` learns per-scene bind-group shapes: the bind group layout,
  pipeline layout, and bind group are rebuilt whenever the scene's field
  count differs from the layout's, and both pipelines recompile against
  the new layout — the rebuild invalidates `compiled_source` *and*
  `overlay_source` (the overlay pipeline shares the layout, so source
  equality alone must not skip its recompile; missing this is the trap in
  this slice). Each field's texture is created and uploaded by the existing
  per-tile verify/upload path, looped over `SceneData::fields` — one
  texture, one bind-group entry each, the failure cache keying on
  `data_key` (manifest + ordered layers) as before. A field-count change
  between scenes (composite → single → composite) rides the same rebuild.
  The no-data stub keeps the n = 1 shape. A field count above the device's
  `max_sampled_textures_per_shader_stage` is rejected with the limit named,
  never truncated.
- Uniform block, samplers, and pipeline shaders otherwise unchanged.

### 4. `sdf-ui` — the composite view

- New `state/scene/composite.rs`:
  - `CompositeSpec { layers: Vec<String> }` derived from the offline config
    at `App::build` (accessor on `OfflineState`, e.g.
    `composite_layers() -> Vec<String>`).
  - A recipe table mapping layer name → WGSL styling snippet. The five
    shipped recipes mirror the shipped scenes' constants (coast
    `smoothstep(122, 132)` ink; river trench band; road/mountain/abyss
    coverage bands); **unknown** layer names get a neutral fallback recipe
    (a gray coverage band at a mid threshold) so the composite degrades
    gracefully when users point it at `road_wagon`/`blur_height`.
    Snippets are templates carrying a `{field}` placeholder; generation
    substitutes the positional helper (`field_0`, `field_1`, …, in config
    order) so the same recipe serves any slot.
  - `scene_source(spec) -> String`: header (`name = "Composite"`,
    `data = "config:sdf/manifest.json"`, `layers = "…"` from config) +
    generated `render` body that paints fields bottom-to-top via
    `field_i(p)`, each mixed over the previous color.
  - Staging reuses the existing machinery: the source's `config:` value is
    rewritten by `resolve_scene_source` and the rewritten copy is parsed
    through `SdfScene::from_file` on a uniquely named temp file — the same
    path `load_rewritten` uses; factor that staging step out so both
    callers share it.
- `App` (`state/app.rs`):
  - `scene_names()` appends `"Composite"` when the spec is non-empty;
  - `select(len)` (the index past the last scene) loads the composite:
    build source → stage → `SdfScene::from_file` → `canvas.set_scene`, with
    load failures surfacing in `load_error`/status bar exactly like scene
    loads. A one-entry composite is allowed (it degrades to a styled single
    field — still useful as the config-driven default view).
  - The composite list is re-derived wherever the library is re-discovered
    after extraction (config does not change mid-run; refresh is for
    symmetry, not necessity).
- `Navigation`: a second section under the scene list — header
  `"Composite"` (`NAVIGATION_COMPOSITE_HEADER`), one button with a distinct
  icon. The pinned gpui-component rev's default icon set has no
  layers/stack glyph; use `IconName::Map` (fallback `LayoutDashboard`),
  `NAVIGATION_COMPOSITE_BUTTON_ID = "composite"`, same `button::variant`
  active treatment as scene buttons. Appended **after** the alphabetical
  scenes so the documented "first file scene is the startup selection"
  contract is untouched; hidden entirely when the array is empty.
  Label collisions with a user scene are possible (a dropped
  `composite.wgsl` naming itself "Composite" lists twice): discovery stays
  parse-free and nothing is reserved — selection is index-based, so both
  entries work, and the contract doc notes the duplicate.
- Constants in `constants.rs`; selectors follow the existing
  `debug_selector` pattern so tests can find the section.

`sdf-component`:

## Risks and known costs

- **GPU memory.** One field ≈ 256 tiles × Σ mip bytes ≈ 90 MB; the default
  five-field composite ≈ 450 MB of texture, allocated on scene switch
  (same per-switch cost class as today's single-field loads, ×N). The
  config array is the lever: drop layers you don't need.
- **Binding budget.** The guaranteed `max_sampled_textures_per_shader_stage`
  is 16 (uniform + field 0 + 2 samplers already use the first slots), so
  composites are validated to ≤ 15 fields with a named error beyond —
  the config array makes hitting it a deliberate act.
- **Upload latency on scene switch.** Every composite (re)select re-reads,
  re-hashes, and re-uploads all fields — the existing
  failure-cache/skip-unchanged logic carries over, but there is no
  cross-composite texture cache in this slice.
- **Recipe drift.** The composite's styling snippets copy constants from
  the shipped scenes; changing a scene file does not change the composite.
  Documented; a user-editable composite scene file is the follow-up that
  fixes it properly.

## Alternatives considered

- **Stack all fields into the existing single `t_field` binding**: one
  bind-group shape survives, but wgpu's guaranteed
  `max_texture_array_layers = 256` fits exactly one 16² field — a ≥2-field
  stack needs raised device limits at bring-up, which risks
  `request_device` failing for every scene (single-field included) on
  constrained hardware. Rejected in favor of per-field bindings.
- **Offline composite export** (a merged `.r8` route): loses per-layer
  styling at render time and bakes order into data; config loses its
  meaning.
- **UI-side alpha blending of N canvases**: N readbacks per frame and map
  scenes are opaque; no.
