# VS-10 — cd-map-offline: user config, game-folder picker, in-app extraction

**Goal:** Make this GUI self-sufficient. It stops depending on a hand-edited
absolute path into `D:\git\cd-data-extract\.work` and becomes its own
install-and-go app: it reads `~/.config/cd-map-offline/config.toml`, offers a
GUI affordance for selecting the Crimson Desert install folder, persists that
choice, extracts the worldmap SDF fields from the game packs (pipeline ported
from the map repo) into `~/.config/cd-map-offline/data/`, and drops the
embedded demo panels so the app opens on real game data only.

**Why this slice:** today the app is a viewer bolted to another repo's
working directory. The shipped `scenes/*.wgsl` files hardcode
`D:/git/cd-data-extract/.work/fields/manifest.json`; on any other machine —
or after cleaning the map repo's `.work` — the app opens on a load-error
overlay. The extraction stack that produces the data lives as a CLI over
there, behind a `config.toml` tuned for that pipeline. This slice moves the
two halves together: config + extraction + viewer in one binary, with the
user-specific fact (where the game is installed) captured through the GUI and
stored where user state belongs.

**Relation to the map repo:** `VS-20.md` there defines the export-manifest
contract (`cd-map-sdf-field`, version 1) this app already consumes
(`sdf-component/src/data.rs`); that contract is unchanged. The migrated
extraction code is ported verbatim where possible; the map repo keeps its
paper / gamedata / render / layer-crop modes and stays the source of truth
for them. Numbered VS-10 here to start this repo's own slice numbering
below the map repo's GUI-facing VS-200.

**Provenance — the Python POC:** the extraction mechanisms this slice
migrates were first derived in a throwaway Python POC at
`C:\Users\tony\AppData\Local\Temp\opencode` (the sanctioned temp workspace
recorded in the map repo's `docs/extraction-map.md`): pack census and the
0012-is-unencrypted finding (`scan_packs.py`), ChaCha20 basename-KDF + LZ4 +
partial-DDS decode (`extract_ui.py`, `lz4_decode.py`, `tail_decode.py`),
tile-grid assembly (`stitch_layers.py`), and field/census structure
(`scan_field.py`, `parse_field.py`). It is a **reference, not a
dependency**: the temp directory can vanish at any time and the Rust port in
the map repo is the authoritative implementation; nothing here may read or
require it at runtime.

## Current state (2026-09-11)

- Workspace: `sdf-app` (binary, gpui entry), `sdf-component` (wgpu canvas +
  scene contract + VS-20 manifest consumer), `sdf-ui` (shell: navigation,
  canvas host, control bar, status bar), `soul-attr`.
- Scenes: `SceneLibrary::discover` scans `scenes/` (`SDF_SCENES_DIR`
  override) for user `.wgsl` files, then appends three embedded demos
  (`metaballs`, `rounded-grid`, `torus-raymarch` via
  `SdfScene::embedded_examples`). File scenes sort first, so a broken data
  scene is the startup view on machines without the map repo's export.
- Data path: scene header `data = <manifest>` resolved relative to the scene
  file; `layer` selects a self-contained manifest entry; payloads (`.r8`,
  one file per tile) are sha256-verified at load. The GUI parses no DDS.
- Extraction (map repo, `crates/map`): `extract` (PAMT parse → PAZ read →
  ChaCha20 → LZ4/partial-DDS reconstruct → `.dds` files + `manifest.json`)
  and `field` (per-prefix 16×16 tile grid → `.r8` payloads + export manifest
  → round-trip gate). Pack `0012` is unencrypted; the ChaCha20 path is
  generic code that stays dormant for these layers.
- The UI has no settings, no persistence, no file dialogs anywhere.

## Data layout (the config home)

Everything user-specific lives under the OS home directory — `~` resolved via
`dirs::home_dir()`; on Windows that is `%USERPROFILE%`. Deliberately **not**
`dirs::config_dir()` (that is `%APPDATA%` on Windows and would scatter the
state).

```text
~/.config/cd-map-offline/
├── config.toml          # tuning + user state (created on first run)
└── data/
    ├── dds/             # extract step output: the game's .dds tiles + manifest.json
    │   └── manifest.json
    └── sdf/             # field step output: .r8 payloads + export manifest.json
        └── manifest.json
```

`config.toml` carries the full extraction surface — the map repo's
config-driven-tuning law survives the migration intact. Defaults (shown)
match the map repo's `config.toml` where the migrated pipeline consumes
them; the layout names fold the old `[paths] work_dir` into `data_dir`:

```toml
# cd-map-offline configuration. Tuning lives here, never in code.
# game_root: the Crimson Desert install directory. Set through the GUI
# picker; contains the pack directory `0012` with its `0.pamt` table.
[paths]
game_root = "D:/SteamLibrary/steamapps/common/Crimson Desert"
data_dir  = ""           # optional override; empty = <config dir>/data

[extract]
packs     = ["0012"]     # the map-screen pack (unencrypted — VS-A phase 1)
includes  = [            # the six worldmap tile families only
    "cd_worldmap_land_sdf*",
    "cd_worldmap_road_sdf*",
    "cd_worldmap_road_wagon_sdf*",
    "cd_worldmap_mountain_sdf*",
    "cd_worldmap_abyss_hex_sdf*",
    "cd_worldmap_blur_height*",
]
dir        = "dds"       # under data_dir: the extracted tiles land here
manifest   = "manifest.json"
dds_header = 128

[sdf.tiles]              # layer → tile-name prefix (export routes)
coast     = "cd_worldmap_land_sdf"
river     = "cd_worldmap_land_sdf"     # same land field; recipes differ
road      = "cd_worldmap_road_sdf"
mountain  = "cd_worldmap_mountain_sdf"
abyss_hex = "cd_worldmap_abyss_hex_sdf"

[sdf.export]
dir      = "sdf"         # under data_dir: .r8 payloads + the export manifest
manifest = "manifest.json"

[sdf.export.extra]       # fields without a recipe scene, exported under a name
road_wagon  = "cd_worldmap_road_wagon_sdf"
blur_height = "cd_worldmap_blur_height"
```

Not carried (no consumer in this app — they stay in the map repo's
`config.toml`): the `[sdf]` decode bands (the scene files are the GUI's
recipe authority, per VS-200), `[render]`, `[paper]`, `[gamedata]`, and
`[layer]` crops.

Disk budget: the five distinct fields export ~85 MiB of `.r8` each (~425 MiB)
plus the extracted `.dds` tiles (real mip0 tiles ~348 KiB each; empty tiles
are 213-byte stubs) — order of 1 GiB total, regenerated idempotently.

## Workstream 1 — app config

New crate `crates/sdf-offline` (library; the only home of config +
extraction, consumed by both the GUI and the CLI).

- `config::Config` (serde/toml, thiserror + error-location per this repo's
  error pattern). The typed structs port from the map repo's
  `config/{paths,extract,sdf,export}.rs` (visibility widened from
  `pub(crate)` to `pub`) and gain `#[serde(default)]` everywhere so a
  minimal file — just `[paths] game_root` — yields the full defaults above.
  `defaults()` is the single source of the default values; the shipped
  `config.toml` example and the tests both assert against it.
- Named constants: `CONFIG_DIR_NAME = "cd-map-offline"`,
  `CONFIG_FILE_NAME = "config.toml"`, `DATA_DIR_NAME = "data"`,
  `PAMT_FILE_NAME = "0.pamt"` (the pack id lives in config now, not code).
- `Config::paths()` → resolved `Paths { config_dir, data_dir, dds_dir,
  sdf_dir, game_root }` — `dds_dir = data_dir/<extract.dir>`,
  `sdf_dir = data_dir/<sdf.export.dir>`, defaults applied, no I/O.
- `Config::load()` → missing file yields `defaults()` (empty `game_root`);
  parse errors surface verbatim with the file path.
- `Config::save()` → **format-preserving edit via `toml_edit`** (the GUI
  writes only `paths.game_root`/`paths.data_dir` into the existing file and
  never rewrites the whole document — hand-tuned `[extract]`/`[sdf.tiles]`
  content and comments must survive a picker round-trip), falling back to
  writing `defaults()` when the file does not exist yet. Atomic: temp file +
  rename, parent dirs created.
- `Config::validate(game_root)` → the install is usable iff
  `<game_root>/<packs[0]>/0.pamt` exists (every pack is checked at extract
  time); the error names the missing path.
- Run-time config validation mirrors the map repo's step-1 guard: empty
  `includes`, a route prefix absent from `includes`, or an
  `[sdf.export.extra]` name colliding with a `[sdf.tiles]` key are hard
  errors before any I/O (the collision check ports from
  `arguments/field.rs::export_routes`).
- Tests: load/save round-trip, default-on-missing, **comment preservation
  through a GUI save**, validation failure messages, data_dir override
  resolution, route-collision rejection.

## Workstream 2 — migrate the SDF extraction

Port from `D:\git\cd-data-extract` `crates/map/src` into `crates/sdf-offline`.
Scope: `extract` + `field` only. Skipped on purpose (stay in the map repo):
`paper`, `gamedata` (PABGB/paloc), `layer` (recipe decode), `render`,
`inspect`, `arguments/paper|gamedata|layer|inspect`, `config/band|crop|
mountain|river|palette|tiling|render|layer`, `dds/header.rs` (BC decode —
needs `texture2ddecoder`), `dds/info.rs` stays (needed by the field step).

| Map repo file | New home in `sdf-offline` |
|---|---|
| `paz/pamt.rs` | `paz/pamt.rs` |
| `paz/entry.rs` | `paz/entry.rs` |
| `paz/compression.rs` | `paz/compression.rs` |
| `paz/crypto.rs` | `paz/crypto.rs` (dormant for pack 0012; attribution comments preserved) |
| `paz/manifest.rs` (`ManifestRecord`) | `paz/manifest.rs` |
| `dds/info.rs` | `dds/info.rs` |
| `dds/partial.rs` | `dds/partial.rs` |
| `sdf/field.rs` | `field/grid.rs` (tile geometry, placement, stub constancy) |
| `sdf/export/*` (kind, tile, tile_payload, mip, layer, manifest, field_map) | `export/*` verbatim |
| `arguments/extract.rs` (`run`) | `run/extract.rs` |
| `arguments/field.rs` (`run` + convert + round-trip) | `run/field.rs` |
| `config/paths.rs`, `config/extract.rs`, `config/sdf.rs` (tiles), `config/export.rs` | `config/*` — ported as the serde structs behind the new `config.toml` (Workstream 1) |

What happens to the map repo's `config.toml` sections:

- `[paths]` → carried: `game_root` keeps its meaning; `work_dir` folds into
  the new `data_dir`; `assets` is dropped (no PNG assets in this app).
- `[extract]` → carried whole: `packs` (defaults to `["0012"]` — the
  gamedata/localization packs belong to the map repo's pipeline and are not
  in the default list, but the key stays config so a pack can be added
  without recompiling), `includes` (defaults to the six tile families), `dir`
  (default `"dds"`), `manifest`, `dds_header`.
- `[sdf.tiles]` → carried whole (the export route table; defaults as in the
  map repo).
- `[sdf.export]` → carried whole: `dir` (default `"sdf"` — was `fields`
  under the old `work_dir`), `manifest`, `extra` (defaults:
  `road_wagon`, `blur_height`).
- `[sdf]` decode bands, `[render]`, `[paper]`, `[gamedata]`, `[layer]`
  crops → **not carried** (no consumer in this app): the recipes live in the
  scene files per VS-200, and verification crops stay in the map repo.

The run functions take `(config: &Config, progress: &mut dyn FnMut(Progress))`
— config-driven exactly like the map repo's, with progress as the new
surface: `Progress` carries step/layer/message so the GUI renders it and the
CLI prints it — one surface, two consumers. Per-file events are batched
every `PROGRESS_EVERY` (named constant, 64); step/layer milestones emit
always. The round-trip gate and per-tile
sha verification port unchanged. Error types rename with the crate:
`MapError` → `OfflineError`, `MapResult` → `OfflineResult` — same
thiserror + error-location pattern, same constructors, no new variants
unless a case genuinely doesn't fit.

Ported tests come with their modules (`field` conversion scenarios, export
round-trip, placement/geometry tests); new tests only for the `run`
wiring against a synthetic fixture in the style the ported tests already use.

## Workstream 3 — GUI: game-folder picker + extraction

`sdf-ui` gains a setup affordance and an extraction surface.

- `AppState` holds an `Entity<OfflineState>` (sdf-offline config + status).
  On startup: `Config::load()`; `game_root` valid → normal boot; empty or
  invalid → the canvas area renders a centered **setup panel** instead of
  (ahead of) the scene list:
  - One-line explanation + the current/empty path.
  - **Select folder…** button →
    `cx.prompt_for_paths(PathPromptOptions { files: false, directories: true,
    multiple: false, prompt: Some("Select the Crimson Desert install folder") })`
    (gpui's platform dialog; the oneshot result is handled in `cx.spawn`).
  - On selection: `Config::validate` (every configured pack's `0.pamt`),
    save config, refresh state. A
    validation failure stays in the panel with the reason — the dialog
    closing with `None` is a no-op, not an error.
  - **Extract now** button (shown once the root is valid): runs the pipeline
    on a dedicated `std::thread` that streams `Progress` events through an
    `mpsc` channel; a `cx.spawn` task on the app thread drains the channel
    (timer-ticked), updates `OfflineState`, and `cx.notify()`s — entity
    mutation stays on the app thread. Progress events land in the status bar
    (step, layer, counts), completion refreshes the scene list. No cancel in
    this slice.
- Reconfigure affordance: a small **game folder** button in the title bar /
  navigation strip reopens the picker at any time (also the recovery path if
  the game moves).
- Status bar: shows `game_root` validity and extraction progress/errors in
  the existing status-line style.
- Failure mode stays the contract's: extraction/manifest problems surface as
  named errors (manifest path, tile, hash), never a silent empty list.

## Workstream 4 — CLI subcommands

`sdf-app` gains clap (thin `arguments/` module; `main.rs` keeps dispatch
only):

- `sdf-app` (no args) → GUI as today.
- `sdf-app extract [--game-root <dir>] [--data-dir <dir>]` → headless:
  load-or-init config, optional flag overrides (not persisted unless
  `--save-config`), run extract + field with progress printed per event,
  exit non-zero on failure (existing `eprintln` + exit pattern).
- `sdf-app config path` → prints the resolved config.toml path (support
  affordance; trivial).

No GPU/gpui initialization on CLI paths — the pipeline is pure std + serde.

## Workstream 6 — scene data resolution + shipped scenes

The scene contract keeps `data`-relative-to-scene-file resolution; one
extension makes the shipped scenes machine-independent:

- `data = "config:sdf/manifest.json"` — the `config:` scheme resolves
  through the app config (`<config dir>` joined with the scheme's remainder).
  **Decided — substitution in `sdf-ui`:** the UI reads the scene file,
  rewrites `config:` values in header directives to the resolved absolute
  path, and loads via `SdfScene::from_str(source, file_stem)`; the component
  crate stays untouched and generic, and the rewrite is a unit-tested pure
  function in `sdf-ui`. Unknown schemes are a parse error naming the value.
- All shipped `scenes/*.wgsl` switch to `data = "config:sdf/manifest.json"`.
  Until extraction has run they fail to load with the missing-manifest error
  (documented behavior) — the setup panel is the intended first-run view.

## Cross-cutting rules

1. **Manifests between every step** — extract writes `data/dds/manifest.json`;
   the field step consumes and re-verifies it (per-tile sha256), then writes
   `data/sdf/manifest.json`; the round-trip gate re-reads every payload.
   Stale/corrupt input is a hard error naming the hash.
2. **The GUI parses no DDS, ever** — container knowledge stays on the
   extraction side; the component consumes raw `.r8` + manifest (VS-200 law,
   already implemented).
3. **One decode path** — the ported field code is assemble-only; no recipe
   thresholds enter the pipeline or the export manifest.
4. **Tuning lives in config.toml, never in code** — the map repo's founding
   law transfers whole: packs, includes, routes, and dir names are
   config-surfaced with code defaults. The GUI's picker writes only
   `paths.game_root`/`paths.data_dir` via a format-preserving edit; it never
   rewrites hand-tuned sections. A config-only change (prune an include,
   rename a route) re-runs the pipeline — no recompile.
5. **Verification is the ported gates, not vibes** — round-trip + sha checks
   ship with the ported code; `just confidence` (fmt/check/clippy/build/test)
   stays clean.

## Decisions (closed)

Every former open issue, resolved and recorded so implementation needs no
further calls:

- **`config:` scheme** — string substitution in `sdf-ui` at scene-load time;
  the component crate is untouched (see Workstream 6). Rationale: one
  feature does not justify widening `SdfScene`'s API; the rewrite is a
  tested pure function.
- **Progress granularity** — the pipeline emits per-file counters batched
  every `PROGRESS_EVERY` (named constant, 64) plus step/layer milestone
  events (`extract: pack scanned`, `field: layer converted`); the GUI
  renders counts, the CLI prints milestones only. Rationale: per-file
  console spam vs. a dead GUI progress readout, split by consumer.
- **Skip-if-unchanged** — rejected for this slice. The pipeline is
  idempotent and manifest-hash-verified, so a re-run is always safe;
  the optimization only pays when extraction time hurts, and it adds a
  staleness-comparison failure class. Trigger to revisit: extraction
  duration becomes a user complaint.
- **Branding** — `APPLICATION_TITLE` becomes `"cd-map-offline"` (matches the
  config home and project identity; taskbar/search findability). The crate
  names (`sdf-*`) stay — renaming crates is churn without payoff.
- **`[sdf]` decode bands** — out of scope, per the "config never ships
  values nothing consumes" rule: the scene files remain the GUI's recipe
  authority (VS-200). Recorded follow-up: surface bands in config and feed
  scenes via the spare `params.zw` uniform when recipe tuning in the GUI
  becomes a real workflow.
- **`data_dir` override** — carried in config (Workstream 1); the default
  empty value resolves to `<config dir>/data`, so it costs nothing until
  used.
